# Eaztrans集运：海外仓整包转寄第一阶段

版本：v3.0 开发验收版，2026-10-23。稳定版保留在 master；本阶段在 feature/overseas-forwarding 开发，不自动发布公网、不修改线上数据库。

## 1. 目标与范围

面向跨境商家。平台内部角色为仓库人员与运营管理员。第一阶段让商家将头程到印尼仓的实际外箱，不拆包转交当地快递，并查看独立尾程费用、收件人和快递单号。

国内预报包裹与海外仓实收外箱是两种对象：国内可能合包，因此不能根据国内包裹数量自动生成海外仓库存。海外仓逐箱确认实物。

本期支持同一商家多批货、不同海外仓库存筛选；每笔转寄限同一头程批次、同一海外仓、一个消费者地址，选择 1–100 个实际整包。一头程可申请多笔尾程。

商品 SKU、拆包、按件拣货、跨头程合并出库、商品多仓分配、电商平台订单同步、快递自动面单/轨迹不在本期。

## 2. 业务流程

1. 头程延续原流程：商家预报 → 深圳仓确认 → 商家付头程一次 → 出货至平台印尼仓。
2. 海外仓选择头程批次，扫描真实外箱标签号；允许分批到货。确认实物全部到齐后，勾选“全部到齐”。
3. 商家在“海外仓”或“我的订单 → 整体订单”选可用整包，填消费者地址、配送地区，查看尾程预估。
4. 提交申请后，所选整包变为“已占用”；该尾程待核价，其他申请无法再次选择这些箱。
5. 海外仓核对地区、距离与依据，按运价确认本尾程费用。
6. 商家提交本尾程的付款凭证 → 运营核实到账审核。头程金额不变；每笔尾程单独付款一次，不设补款状态。
7. 审核通过进入“待出库”。整包已完整包装，不再进入打包确认；海外仓交承运商并登记实际快递单号。
8. 商家、仓库在同一整体订单查看各尾程地址、费用和快递单号，复制后去承运商官方渠道查询。
9. 仓库依据真实签收结果人工登记签收，只更新该尾程及对应整包；其余外箱继续留仓或待其他尾程配送。

```mermaid
flowchart LR
  A[头程已付款并出货] --> B[海外仓逐箱到货]
  B --> C[可转寄整包]
  C --> D[商家选箱与消费者地址]
  D --> E[占用整包 / 仓库核价]
  E --> F[商家提交凭证]
  F --> G[运营审核到账]
  G --> H[整包出库 / 快递单号]
  H --> I[人工核实签收]
  E -->|未提交待审凭证且未付款时取消| C
```

## 3. 页面与递进入口

| 角色 | 主菜单 | 递进入口与操作 |
| --- | --- | --- |
| 商家 | 海外仓 | 库存筛选 → 选择整包转寄 → 消费者地址与预估 → 本尾程费用/付款 |
| 商家 | 我的订单 | 整体订单 → 头程、实际外箱、多笔尾程 → 费用或物流详情 |
| 仓库 | 海外仓到货 | 头程批次 → 扫描外箱 → 分批确认或全部到齐 |
| 仓库 | 海外仓包裹 | 按仓、箱号、状态查询 → 来源整体订单 |
| 仓库 | 仓库工作台 | 尾程任务 → 核价 → 待付款 → 直接整包出库 → 物流/签收 |
| 运营 | 付款审核 | 单笔尾程凭证 → 核实金额/流水 → 审核通过或退回凭证 |
| 运营 | 渠道 / 箱型 / 运价 | 尾程地区运价；海外仓人员权限分配或移除 |

付款凭证退回仅补交资料，不要求再次转账。未上传凭证不代表已付；登记单号不代表已签收。

## 4. 状态与一致性

| 对象 | 状态推进 | 规则 |
| --- | --- | --- |
| 海外仓实际整包 | available → reserved → dispatched → delivered | 取消未付款申请可从 reserved 返回 available |
| 整包转寄尾程 | warehouse_received → awaiting_payment → paid → shipped → delivered | paid 显示待出库，跳过打包；未付款且无待审/已通过凭证可取消 |
| 头程批次到货 | 未到货 → 部分到货 → 全部到齐 | 部分到货即可申请实收整包；全部到齐后不能追加新箱 |
| 整体订单 | 汇总库存与所有有效尾程 | 全部到齐、所有实收箱签收、所有未取消尾程签收后，才显示整体已签收 |

头程数据库状态保留 shipped；到印尼仓用 overseas_received_at 表示。整体进度由实际外箱及全部尾程汇总，不强行覆盖头程状态。取消尾程保留历史与原选箱关联，不计为有效配送任务。

操作保存后刷新三端数据；后台每 10 秒轮询，已有订单实时订阅也会触发刷新。正在填写的表单不被轮询覆盖，提交时数据库重新校验库存、权限、运价版本和付款。

## 5. 数据字典

| 表 / 字段 | 含义 |
| --- | --- |
| orders.forwarding_enabled | 头程已使用实际海外外箱模式，默认 false |
| orders.fulfillment_mode | 新尾程为 whole_package；历史单保留原值 |
| orders.overseas_receiving_completed_at | 本批所有实物已到齐的确认时间 |
| orders.parent_order_id | 每笔尾程所属头程；同一头程可有多笔 |
| orders.forwarding_request_id / payload | 商家提交幂等标识及内容快照；同号同内容重试返回原单 |
| overseas_packages.id / package_no | 实际外箱 UUID / 仓库标签号；同一仓箱号唯一 |
| overseas_packages.source_order_id | 来源头程批次 |
| overseas_packages.merchant_id / overseas_warehouse_id | 货主与实物所在海外仓 |
| overseas_packages.status / assigned_order_id | 可用、占用、出库、签收，以及当前占用尾程 |
| overseas_packages.received_by / received_at | 实际入库人员和时间 |
| overseas_packages.dispatched_at / delivered_at | 出库和签收时间 |
| overseas_packages.note | 到货备注，最多 500 字 |
| forwarding_order_packages.order_id / package_id | 尾程选箱历史；取消后仍保留，可追溯再次分配 |
| overseas_warehouse_staff.user_id / warehouse_id | 仓库人员实际可作业的海外仓，多对多 |
| fees / payments / payment_receipts | 沿用既有独立账单、审核付款和私有凭证体系 |

新增表开启 RLS，浏览器只有查询权限，写操作统一走数据库函数。商家只能看本人箱；仓库只能看分配的海外仓。国内仓归属不自动授予海外仓作业权限。

关键函数：warehouse_receive_overseas_packages、merchant_create_forwarding、merchant_cancel_forwarding、warehouse_dispatch_forwarding、admin_set_overseas_staff。旧出货与签收函数兼容路由；旧尾程建单和整批到货函数停止新增，避免绕过库存约束。

## 6. 验收

自动验收：`npm test` 覆盖页面与状态；`npm run test:db` 在本地 PostgreSQL 中加载全部迁移，重复执行新迁移，再进行事务回滚测试。

本次结果：94 项自动测试通过；数据库五组验收及迁移重复执行通过。浏览器已实测双箱入库、第一箱独立报价/测试凭证/运营审核/直接出库、第二箱不同消费者申请，以及商家运单复制与整体订单多尾程展示。取消释放和人工签收规则通过数据库验收；真实承运商与真实资金交易未测试。

数据库五组验收：

1. 权限、人员分配、部分到货、重复扫码、禁止直接写库存。
2. 缺失/重复箱号、不完整地址、过期运价、重复提交幂等、同箱重复占用冲突。
3. 未付款禁止出库、取消释放、第二批入库、全部到齐后禁止新增、一头程多笔消费者尾程。
4. 独立核价与付款审核、审核中/已付款不可取消、出库不等于签收、重复出库幂等、禁止覆盖单号、签收不影响其他箱。
5. 跨商家库存隔离、旧建单接口不可绕过库存。

浏览器人工验收顺序：

1. 本地测试仓库录入 BOX-001、BOX-002，并标记全部到齐。
2. 切商家，仅选 BOX-001，填地址 A、地区并提交；确认 BOX-002 仍可转寄。
3. 切仓库确认尾程费用；切商家提交带测试水印凭证。
4. 切运营填写同额模拟到账、唯一测试流水，勾选模拟测试后审核通过。
5. 切仓库工作台，确认“待出货”可直接登记整包承运商及单号，没有二次打包按钮。
6. 切商家核对整体订单与库存：第一箱已出库，第二箱仍可转寄，整体未签收；复制运单。
7. 第二箱申请地址 B，付款前取消，确认库存恢复；重新申请后保留各次历史记录。
8. 实际签收第一箱后，确认第二箱及其他尾程不被错误签收。

本地测试环境使用 PGlite、模拟 auth/storage 适配和内存图片，证明数据库规则及页面闭环；不等同于线上 Supabase Auth、Storage、Realtime、承运商接口验收。

## 7. 本地使用与发布

本地：Node.js 20+ → npm ci --ignore-scripts → npm run dev:forwarding → http://127.0.0.1:4175/。仅监听本机，测试角色无密码，不能作为公网服务。关闭终端或重启服务会清空所有本地测试数据；不会清空线上数据。

开发分支的 index.html 仍保留正式 Supabase 配置，仅本地启动服务会替换为隔离适配器。**请使用上面的本地启动方式测试，不要把开发分支直接放到公网去连接正式数据库。** 如需远程联调，先建立独立 Supabase 开发项目并替换配置，不提交 secret/service_role 密钥。

发布前步骤：

1. 完成开发分支测试；在独立 Supabase 开发项目验证真实 Auth、私有凭证上传、RLS、三端刷新及历史订单展示。
2. 备份正式数据库及凭证存储，确认未结算历史尾程处理方案。
3. 迁移基线必须为完整 v2.2。全新开发库顺序：schema、warehouse-operations、admin-operations、merchant-workspace、parcel-maintenance、parcel-estimates、payment-review、sea-route、separate-settlement、overseas-addresses、cargo-channels、last-mile-pricing，最后 overseas-forwarding。
4. 正式发布应暂停旧页面写入，在维护窗口迁移 overseas-forwarding.sql 并发布匹配前端，不能让旧前端继续写新版库存。
5. 运营为海外仓人员分配权限；真实业务维护仓库地址和尾程运价，核对收款配置。
6. 小批人工实物试运行通过后再扩大使用。签收仍需人工核实，真实承运商接口另期接入。

迁移可重复执行，但不是自动回滚脚本。稳定标签只备份代码；新库存和多尾程产生后，不可仅切回旧前端，需停止写入、保留数据并制定兼容回退方案。

## 8. 历史单与迭代记录
