## v2.1 运输计算器与普货 / 敏感货渠道

在 v2.0 基础上执行 `supabase/cargo-channels.sql`，再部署配套前端。迁移补充货物类型及海运重量单价，保留原有线路代码、运营自定义线路名称、已有订单和已确认费用。新增渠道重复执行不覆盖运营维护的运价。

- 商家菜单「运输计算器」：深圳仓 → 平台印尼仓，填写每组外箱尺寸、每箱重量及相同箱数；最多20组，每组100箱，总箱数1000。支持增删、重置和展开分箱明细。改尺寸、箱数或渠道后清除旧结果，重新计算；试算不创建订单、不收款。
- 四类渠道：空运普货 `ID-AIR`、空运敏感货 `ID-AIR-SENSITIVE`、海运普货 `ID-SEA`、海运敏感货 `ID-SEA-SENSITIVE`。申请打包、仓库核价和运营运价配置共用这些渠道。货物是否适合某条渠道仍需仓库核实。
- 空运：总实重与总体积重取大，按本渠道首重 / 续重规则计费。海运：体积费＝总体积与最低体积取大 × 每立方单价；重量费＝总实重 × 每公斤单价；头程取两项较高值，再加每票国内仓操作费。页面同时显示两项费用与采用依据。印尼仓至消费者的尾程不计入此预估，仍另单核价付款。
- 新增空运敏感货测试价：首重0.5kg ¥88、续重¥52/kg、操作费¥18。海运普货升级时保留原体积单价及最低体积，补充测试重量价¥1.50/kg；海运敏感货测试价¥800/m³、最低0.1m³、重量¥2/kg、操作费¥18。新增及海运变更明确标为测试运价，正式运营前在后台替换实际报价。
- 运营可分别维护每条线路的价格、海运重量单价及启停。仓库确认费用保存完整运价快照；旧海运账单仍显示原体积计费，新配置不重算已确认金额。运价保存带角色、版本校验与审计；运价时间戳递增，连续保存也不能用旧版本覆盖。

验收：`node --test tests/*.test.cjs`；`supabase/cargo-channels-qa.sql` 在事务中验证四类渠道下单、仓库实际计费、运价快照、价格维护和旧单金额保留，末尾回滚。计算例：100×50×40cm、100kg，普货体积费¥120、重量费¥150，取¥150，加操作费¥18，合计¥168；仅为测试价格。

## v2.0 包裹进度与自动同步

在 v1.9 基础上执行 `supabase/progress-realtime.sql`，将既有订单、包裹、物流节点及付款通知表加入 Supabase Realtime publication，保留原有权限和行级访问规则。重复执行不会重复添加。

“我的包裹”的状态、筛选数量和详情共用头程 / 尾程进度：头程运输中 → 已到印尼仓 → 待尾程报价 / 付款 / 出库 → 尾程派送中 → 已签收。尾程通过头程关联到原包裹，不新增重复包裹。取消尾程后恢复头程状态，异常包裹保留异常提示。

已登录的查看页面订阅数据库变化，收到通知后重新读取当前账号有权查看的数据。实时连接正常时每30秒额外校验；连接未建立时每10秒检查；恢复网络或返回页面时重新同步。顶部显示连接状态和最近同步时间。自动刷新保留筛选、分页与滚动位置；正在填写、未提交搜索或提交操作时暂缓应用，离开表单后继续。退出、换账号及后台页面会清理旧订阅，过期异步读取结果不覆盖新页面。

此功能同步的是仓库与运营登记的业务进度，尚未接入承运商自动物流接口。无需另行批量改写物理包裹状态来表示海外仓或尾程阶段。

验收：`node --test tests/*.test.cjs`，覆盖进度映射、数量和筛选、事件合并、表单保留、网络恢复、账户切换及过期请求隔离。

## v1.9 头程平台仓与尾程消费者地址分离

在 v1.8 基础上执行 `supabase/overseas-addresses.sql`，再部署配套前端；请勿重跑旧迁移覆盖新函数。迁移保留已有订单、地址、账单及付款，禁止旧版按消费者地址创建头程的入口。

- 我的包裹 → 申请打包 / 合包：直接选择平台印尼仓，不要求先保存消费者地址。头程订单保存仓名、详细地址及联系人快照。
- 我的订单 → 头程详情：未到印尼仓时显示尾程入口说明；登记到仓后出现“申请尾程配送 · 独立结算”。填写消费者姓名、电话、城市、详细地址、选填邮编，可选地址簿后修改；不默认复制头程仓地址。创建后进入独立尾程订单，报价后在该单付款。
- 运营后台 → 线路与运价配置 → 平台印尼仓地址配置：可维护仓地址、联系人、电话及测试标记。保存有版本校验与审计，已有订单地址快照不变。

初始印尼仓是明确标记的 **测试占位、禁止寄件** 记录：Jakarta 雅加达，TEST WAREHOUSE ONLY，电话 TEST-NOT-A-PHONE。正式运营前必须替换成真实资料。旧版历史账单不会自动生成尾程，避免重复收费；当前仍为整票一笔尾程、一个消费者地址。

验收：`node --test tests/*.test.cjs`，以及 `supabase/overseas-addresses-qa.sql` 全事务回滚，验证仓地址快照、消费者地址必填、商家与运营权限、分段付款与签收、幂等及配置版本冲突。

## v1.8 海运与头程 / 尾程独立结算

现有 v1.6 项目顺序执行 `supabase/sea-route.sql`、`supabase/separate-settlement.sql`，再部署配套前端。前一份建立海运 / 体积计费基础，后一份启用最终的 **分开付款** 业务规则，并关闭合并收费入口。请勿再执行旧费用函数覆盖新版。

商家申请打包可选印尼空运或海运。空运按计费重量；海运按外箱体积合计与最低计费体积计费。海运初始 **¥600/m³、最低0.1m³、国内仓操作费¥18** 仅为测试数据，运营可在“线路与运价配置”分别维护实际报价。本版未接承运商自动报价。

最终流程：

1. 头程订单：深圳仓收货测量 → 确认头程运输费及国内仓操作费 → 商家提交头程凭证 → 运营审核 → 打包并登记头程出货。
2. 仓库在头程出货详情中核实并登记实际印尼海外仓到货、仓名及位置。此操作不代表消费者签收。
3. 商家在头程订单详情申请尾程，独立填写消费者地址或选择本人保存的印尼地址；生成关联的独立尾程订单，不复制头程包裹关联，不重复收头程费。
4. 尾程单直接进入仓库待报价队列 → 仓库填写人民币报价及依据 → 商家提交尾程付款凭证 → 运营按尾程金额独立审核 → 尾程出库准备及发货 → 核实后登记消费者签收。

每段使用自己的订单、费用、凭证、付款和物流记录，一段一次付款；尾程不是头程补款。未报价不伪造0元，尾程当前只支持正数人工报价，汇率依据写在说明中。本版一票头程只创建一笔尾程，整票发往一个消费者地址；不含海外仓库存管理、分批拆票、多消费者配送或真实自动轨迹。内部仓库账号沿用已有业务归属与权限，尚未新增独立海外仓员工权限系统；登记的仓名与位置应由有权限人员核实填写。

历史订单与已确认 / 已付金额不重算，旧账单显示未拆分；旧账单不可自动创建尾程单，以免重复收费。迁移不清空测试数据。账单CSV含每段费用与关联信息，三端共用费用记录。

验收：48项前端测试；`supabase/separate-settlement-qa.sql` 事务内验证头程78、尾程25分别提交凭证 / 审核 / 锁定 / 出货、到仓门禁、角色权限、幂等创建、尾程签收及头程金额不变，末尾全部回滚。本地嵌入式 PostgreSQL 也验证迁移可重复执行。回滚SQL只模拟图片元数据，真实私有文件上传沿用 v1.6 流程。

## v1.6 转账凭证与运营审核

在现有业务补丁之后，最后执行 `supabase/payment-review.sql`，不要再执行旧版付款函数覆盖此补丁。已部署项目当前启用虚拟人民币账户：演示银行（不可转账） / Mospace 虚拟收款账户 / `DEMO-NOT-A-BANK-0001`。这不是银行账号，不接受真实转账。

测试流程：仓库确认最终费用 → 商家订单详情 → 自动生成测试凭证并提交 → 运营「付款审核」填写模拟金额、唯一测试流水并勾选测试确认 → 审核通过 → 商家和对应仓库收到站内通知 → 仓库打包 → 待出货。退回只补充凭证，不要求再次转账。提交凭证本身不会生成付款记录或放行仓库。

运营「收款账户」支持启停、测试/真实模式和账户资料维护，暂只支持 CNY。真实模式需填写自有账户，并逐笔核查银行实际到账；此版未接支付网关、自动扣款、自动银行对账或短信。历史旧版演示付款保留，不视为银行到账审核。工作台每30秒检查站内通知，其他页面可手动刷新。

凭证为私有图片，限制 PNG/JPEG/WebP、5MB。商家仅查看本人凭证，运营可审核，仓库不读取凭证。预览链接60秒过期；前端不使用公开图片链接。失败上传可能留下未关联的私有文件，暂不自动删除。

本次验证：`node --test tests/*.test.cjs`（39项）；`supabase/payment-review-qa.sql` 在事务内模拟角色、存储元数据、审核/退回/补交、通知、打包和出货并全部回滚。该 SQL 不替代真实浏览器 Storage 上传验证；本地浏览器夹具用于验证三端页面交互，不写入线上业务数据。

## 接入 Supabase

1. 打开 Supabase 项目的 SQL Editor：
   https://supabase.com/dashboard/project/bdxqphmzwojamyuboqmz/sql/new
2. 打开 `supabase/schema.sql`，复制全部内容到 SQL Editor。
3. 点击 **Run**。成功后会创建商家、仓库、订单、包裹、费用、付款、物流事件和审计日志等表，并启用角色权限。
4. 在 Authentication → Users 中注册的第一个账号会自动生成 `merchant` 商家档案。仓库操作员和管理员账号需要后续由管理员授予角色。

5. 执行 `supabase/member-login.sql`。它会为每个账号生成唯一会员号（格式如 `M12345678`），并创建会员号到 Supabase Auth 邮箱的安全解析函数。

如果创建订单时出现 `new row violates row-level security policy for table "orders"`，请执行 `supabase/fix-order-insert.sql`。这是已有账号缺少商家档案时的兼容补丁。

订单创建后，继续执行 `supabase/warehouse-operations.sql`，页面才会把仓库入库、确认实重尺寸、打包和出货写入数据库。仓库操作必须使用 `profiles.role = 'warehouse_operator'` 且绑定 `warehouse_id` 的账号；商家账号只能查看自己的订单并完成一次付款。

后台运价和地址页面还需要执行 `supabase/admin-operations.sql`：它会创建 `route_pricing` 运价表、管理员保存运价 RPC 和审计记录。执行后，管理员端“保存配置”、商家端“保存收件地址”、仓库端按真实快递单号匹配都会使用数据库。

完整试运行顺序：商家创建订单 → 仓库端“入库扫描”输入订单中的快递单号并匹配 → 包裹确认录入实重尺寸 → 商家费用页一次付款（当前记录人工转账结果）→ 仓库打包 → 出货登记 → 商家物流追踪。真实微信/支付宝支付网关仍需单独接入，当前不会产生真实扣款。

登录规则：登录可填写会员号或注册邮箱，再输入密码；注册时填写邮箱和密码，完成邮箱验证后，系统会在商家档案中生成会员号，注册提示会显示该会员号。仓库操作员和管理员也使用会员号或邮箱登录，实际工作台由 `profiles.role` 权限决定。页面不再收集公司名称。

业务规则已经写入数据结构：商家先发货到深圳仓；仓库确认实重和尺寸后进入待付款；每个订单只有一条付款记录，付款后费用锁定，不设计待补款或二次付款。

## 当前边界

订单创建、订单列表、包裹列表和物流轨迹已经接入 Supabase。仓库作业补丁使用初版印尼空运计费规则：首重 0.5kg ¥68，续重 ¥42/kg，仓库操作费 ¥18；后续可再把运价规则抽成管理员配置表。当前付款按钮记录的是一次“人工收款/线下转账”结果，还没有接微信支付或银行卡支付网关。
